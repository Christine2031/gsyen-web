# GSYEN 自研邮件系统迁移至阿里云基础设施（P0）

状态：规划与盘点阶段，禁止生产切换  
决策日期：2026-08-24  
优先级：P0

现网只读基线与当前阻断项见
[`GSYEN_MAIL_MIGRATION_BASELINE_2026-08-24.md`](GSYEN_MAIL_MIGRATION_BASELINE_2026-08-24.md)。

## 决策与目标

`gsyen.com` 是 GSYEN 的核心邮件域，也是账号体系和多个业务服务的关键依赖。
项目决定保留 GSYEN 自研邮箱的账号、地址、别名、收件、发件、文件夹、同步、
审计和运维逻辑，将承载这些逻辑的计算、数据库、对象存储、消息队列、日志与网络
逐步迁移到阿里云基础设施。

**阿里企业邮箱不是目标产品，也不得替代 GSYEN 自研邮箱。** Google、Cloudflare
Email Routing、D1、R2、Queues、Resend、Vercel、Cloud Run、GCS 和 Supabase 是
需要逐项盘点的现有依赖，不等于目标业务模型。

迁移必须同时满足：

1. 不丢失历史邮件和迁移期间的新邮件；
2. 切换期间持续收发，避免业务可感知中断；
3. 保持现有邮箱地址、账号映射和关键依赖兼容；
4. 任一关键验证失败时可以在既定窗口内回滚；
5. 所有生产变更都有责任人、时间戳、变更记录和验证证据。

## 生产冻结规则

在项目负责人明确确认以下三项之前，不得进入生产切换：

- 阿里云目标地域、VPC、计算、数据库、存储、队列和 SMTP 入站/出站方案；
- 迁移时间窗口、冻结窗口与各阶段责任人；
- 经演练验证、可以实际执行的回滚方案。

确认前明确禁止：

- 修改生产 MX、SPF、DKIM、DMARC 或其他邮件相关 DNS；
- 停用、删除或降级 Google / Google Workspace、Cloudflare、Resend 或现有邮件服务；
- 删除邮箱、别名、群组、转发规则、历史邮件、日志或密钥；
- 执行不可逆的账号合并、数据清理或域所有权迁移；
- 将未经验证的阿里云配置声明为生产主链路。

当前允许的工作仅限盘点、文档设计、只读查询、导出备份、测试环境验证和演练。

## 第一阶段：现网盘点

### 邮箱与数据

- [ ] 导出所有用户邮箱：主地址、状态、容量、许可、最后登录时间；
- [ ] 导出全部别名、共享邮箱、资源邮箱、群组及成员关系；
- [ ] 导出转发、自动回复、收件规则、委派权限、Send As / Send on behalf；
- [ ] 统计历史邮件数量、容量、最大单封邮件、附件类型和时间跨度；
- [ ] 识别归档、保留、诉讼保全、Vault、审计及合规要求；
- [ ] 记录联系人、日历等是否属于本次迁移范围，默认不得隐式纳入。

### DNS 与投递链路

- [ ] 保存权威 DNS 当前完整快照和 TTL；
- [ ] 记录 MX、SPF、DKIM selector、DMARC、MTA-STS、TLS-RPT、BIMI；
- [ ] 识别所有通过 `gsyen.com` 发信的系统、SMTP/API 凭据和固定 IP；
- [ ] 识别退信、投诉、邮件追踪、归档和安全网关链路；
- [ ] 收集主要收件方的 SPF、DKIM、DMARC 当前通过率与投递基线。

### 账号与业务依赖

- [ ] 核对邮箱地址与 GSYEN / HalfSphere / Supabase 用户 ID 的映射；
- [ ] 识别以 `@gsyen.com` 作为登录名、找回邮箱或 MFA 通道的服务；
- [ ] 识别 Google OAuth、Gmail API、SMTP Relay、群组权限和 SSO 依赖；
- [ ] 识别 `mail-api.gsyen.com`、GSYEN Mail Worker、Cloudflare Email Routing、
      Resend 与 Google Workspace 的真实生产职责和流量边界；
- [ ] 为每项依赖指定负责人、验证方法、迁移策略和回滚策略。

> 现有仓库文档（2026-07-29）记录 Cloudflare Email Routing + Resend 已承担部分
> 根域收发能力，而本次决策指出现有 Google / Google Workspace 体系仍需迁移。
> 两者必须通过控制台、DNS、日志和真实邮件探针核实，旧文档不能直接作为现网事实。

## 第二阶段：目标架构与迁移设计

完整的全栈目标架构见
[`GSYEN_ALIYUN_FULLSTACK_MIGRATION.md`](GSYEN_ALIYUN_FULLSTACK_MIGRATION.md)。
阿里云具体资源规格未确认前，不创建付费生产资源。方案评审至少覆盖：

- 邮箱账号、别名、群组、共享邮箱和管理员权限的目标模型；
- MX、SPF、DKIM、DMARC 的最终记录、共存记录和长度限制；
- DNS TTL 降低与恢复计划，以及各递归解析器的传播观察窗口；
- 历史邮件导入工具、批次、吞吐、失败重试、校验和差异补同步；
- Cloudflare 入站与阿里云自研 SMTP 入口并行运行、双投递或邮件路由策略；
- 迁移期间新邮件的增量同步和最终差异收敛；
- 客户端、移动端、SMTP/API、SSO、MFA 与账号体系兼容；
- 日志、审计、告警、退信、投诉、垃圾邮件和容量监控；
- 数据驻留、备份、恢复、保留和合规要求。

## 第三阶段：演练与分批迁移

1. 使用非核心测试域或受控测试账号完成端到端演练；
2. 选择低风险试点邮箱，先同步历史邮件，再验证增量同步；
3. 验证内外部收发、回复/转发、别名、群组、附件和中文编码；
4. 验证 SPF、DKIM、DMARC、退信处理、垃圾箱判定和投递延迟；
5. 验证 GSYEN 登录、注册、找回、通知及邮件 UI 不受影响；
6. 执行一次完整回滚演练，并记录实际恢复时间；
7. 试点验收后才允许提出生产切换申请。

## 生产切换准入门槛

以下事项必须全部有证据并经负责人确认：

- [ ] 账号、别名、群组、规则、依赖和邮件总量盘点已签字确认；
- [ ] 全量同步完成，抽样和统计校验通过；
- [ ] 增量同步延迟处于约定范围；
- [ ] SPF、DKIM、DMARC 方案通过测试且不存在冲突；
- [ ] 并行运行和切换步骤已有逐分钟 runbook；
- [ ] 监控、告警、支持联系人和升级路径已就绪；
- [ ] 回滚已演练，并验证旧系统仍能正常收发；
- [ ] 阿里云基础设施清单、预算、时间窗口和回滚方案获得明确批准。

## 回滚基线

最终 runbook 必须保存切换前 DNS 快照和旧服务配置，并至少规定：

1. 哪些指标触发停止或回滚；
2. 谁可以批准回滚，谁执行 DNS 和路由变更；
3. 如何恢复旧 MX、发信通道和账号访问；
4. 如何处理切换窗口内已进入阿里云的新邮件；
5. 如何避免重复投递、重复导入和邮件丢失；
6. 回滚后如何验证内外部收发与 GSYEN 账号流程；
7. 在完成审计前保留双方系统、日志、导出和迁移报告。

## 当前待决策事项

- 阿里云主地域、灾备地域、网络拓扑和预算上限；
- 自研 SMTP 入站方案及阿里云对邮件服务器用途、TCP 25、固定 IP、PTR 的书面确认；
- 出站首期继续使用 Resend，还是接入阿里云邮件推送作为可插拔 provider；
- Supabase 首期保留还是自托管迁移，以及相应的 Auth/JWT 兼容方案；
- 是否迁移联系人、日历、Drive 或仅迁移邮件；
- Google Workspace 退出或保留时长；
- 并行运行方式与可接受的最大同步延迟；
- 迁移批次、正式切换窗口和业务冻结窗口；
- 回滚目标时间（RTO）与可接受数据差（RPO）；
- 邮件保留、归档、审计和数据驻留要求。
